## Root-cause status, missing validation and recommendation

**Confirmed:** a native Windows XPU functional failure in the original where reproduction, with the expected CPU result and correct initial mask transfer. **Unconfirmed hypotheses:** wheel-specific code generation, runtime/stream integration, and buffer/copy/initialization/lifetime interactions in the compaction path. Neither a generic scan bug, the host null-sentinel/std::distance path, nor an allocator defect has been established. The diagnostic custom operators do not replace or override aten::where/nonzero. Their successes are not a patched-Torch after-pass.

The exact pinned XPU allocator source (`10d343709a20ce78d760bbeb518635616fb818b56e15877e9bf37ed7a8007c8f`) and installed XPU memory API did not expose a supported no-cache switch. No guessed environment flag was used. This is an unsupported diagnostic-control limitation, **not** an unavailable-hardware or terminal environment blocker.

The material remaining gap is a demonstrated source-level cause/minimal production fix together with a matched native PyTorch build that fails before and passes after that change. Native MSVC/SYCL compilation is available and was exercised; the portable custom-op route does not rebuild the official wheel's kernels under its exact compiler/flags. No actual changed-PyTorch validation, relevant patched regression suite, or patched binary provenance exists. No speculative fill/zeros/scan rewrite or personal-fork code PR was created merely to obtain a PR.

Recommended next step: establish the official nightly's matched compiler/build recipe and instrument the actual PyTorch small-N compaction/count/scatter boundaries in an unmodified native Windows build. Reproduce the wheel failure there before testing a minimal fix. Independently vary prefill/touch and synchronization using otherwise identical live buffers; do not infer an allocator cause from the confounded 24/24 control. Validate any candidate in real changed PyTorch binaries on DEV_7D67 and, ideally, on the reporter's DEV_7D51/driver arrangement.
